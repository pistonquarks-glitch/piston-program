  ## Hallazgos críticos

  1. kernel sería un “god module”.
     Sesiones, eventos, permisos, configuración, plugins, memoria y comunicación no
     deben vivir bajo una misma responsabilidad. El núcleo debe coordinar; no
     convertirse en dueño de todos los dominios.

  2. El “Traductor Universal” estaba sobredimensionado.
     Traducir MCP, CLI, REST, gRPC, archivos, formatos y SDKs en un único
     componente produciría una abstracción poco precisa y acoplada. Debe traducir
     únicamente hacia el contrato de capacidades de Piston; cada protocolo externo
     conserva su adaptador independiente.

  3. context, memory, storage y workspace se solapaban.
     Su separación inicial generaría dependencias circulares previsibles: agente →
     contexto → memoria → almacenamiento → sesión → agente. No deben nacer como
     paquetes autónomos hasta existir casos de uso que justifiquen sus fronteras.

  4. model-gateway y tool-runtime no son núcleo.
     Un proveedor de modelo y una herramienta son dos clases de capacidad. Deben
     entrar por el mismo mecanismo extensible, no como subsistemas privilegiados.

  5. products necesitaba ser “product packs”, no aplicaciones.
     Piston Gold, Music y Video no deben tener lógica propia ni replicar un host.
     Serán manifiestos de composición: agentes, plugins, políticas, flujos y UX
     habilitada.

  6. Faltaba separar plano de control y plano de ejecución.
     Los agentes autónomos no deben ejecutarse dentro de la UI ni bloquearla. VS
     Code está migrando hacia un Agent Host dedicado que conserva sesiones
     independientemente de los clientes; es un principio muy aplicable a Piston. VS
     Code Agent Host
     (https://code.visualstudio.com/docs/agents/concepts/agent-host)

  7. El sistema de plugins necesita ubicación, activación y permisos desde el
     contrato.
     VS Code aísla extensiones, las activa de forma perezosa y distingue ejecución
     local, web o remota. IntelliJ exige declarar dependencias y módulos
     opcionales. Piston debe adoptar esos principios, sin copiar sus APIs. VS Code
     Extension Host
     (https://code.visualstudio.com/api/advanced-topics/extension-host) · IntelliJ
     Modular Plugins
     (https://plugins.jetbrains.com/docs/intellij/modular-plugins.html)

  8. El núcleo remoto debe exponerse por una única frontera.
     Si llega a existir servidor remoto, los clientes y nodos no deben hablar entre
     sí libremente. Un API central tipado evita acoplamientos laterales, como el
     patrón hub-and-spoke de Kubernetes. Kubernetes control-plane communication
     (https://kubernetes.io/docs/concepts/architecture/control-plane-node-communication/)

    recibir resultados/eventos. Es el alcance correcto del Traductor Universal.

  - Adaptadores: MCP, CLI, REST, GraphQL, gRPC y SDKs se implementan como
    extensiones; no contaminan el Core.

• ## Veredicto

  Arquitectura V2 aprobable con cambios. La visión de Piston es sólida, pero la
  estructura anterior todavía trataba demasiadas ideas como paquetes
  independientes. La versión final debe reducir el núcleo, convertir “Traductor
  Universal” en un límite de adaptadores y separar coordinación, ejecución de
  agentes y ejecución de extensiones.

  No he creado ni modificado archivos.

  ## 1. Problemas encontrados

  - Núcleo sobredimensionado: kernel acumulaba sesiones, eventos, permisos, plugins
    y configuración. Eso acabaría como un “god module”.

  - “Traductor Universal” ambiguo: no debe traducir “todo”: formatos de video, PDF
    o MIDI no son protocolos de herramientas. Su misión debe limitarse a adaptar
    capacidades externas al protocolo interno.

  - Sesgo hacia desarrollo de software: workspace no representa bien documentos,
    música, video o investigación. Debe convertirse en un concepto más general de
    recursos y artefactos.

  - Separación prematura: context, memory, storage, scheduler, event-bus, tool-
    runtime y observability como paquetes iniciales generarían interfaces vacías y
    dependencias artificiales.

  - model-gateway privilegiado: un modelo es una capacidad, igual que un navegador,
    compilador o conector MCP. No necesita un subsistema central especial.

  - Productos potencialmente duplicados: Piston Gold, Music y Video deben ser
    paquetes declarativos de composición, no apps con runtime propio.

  - Plugins sin modelo de ubicación: un plugin puede requerir UI, workspace local,
    ejecución remota o navegador. El manifiesto debe declarar dónde puede correr,
    capacidades, activación y permisos. VS Code ilustra bien esta separación e
    inicio perezoso. VS Code Extension Host
    (https://code.visualstudio.com/api/advanced-topics/extension-host)

  - Falta un límite explícito de credenciales y confianza: un plugin no puede
    recibir secretos ni permisos por el simple hecho de declararlos.

  - Riesgo de dependencia circular: agente → contexto → memoria → almacenamiento →
    sesión → agente.

  - Exceso de infraestructuras futuras: gateway, web, infra y servicios remotos no
    deben condicionar la primera versión local.

  ## 2. Riesgos a corto plazo

  - Diseñar demasiados contratos antes de tener un flujo completo de Piston Code.
  - Convertir el bus de eventos en mensajería genérica sin semántica ni
    persistencia.

  - Ejecutar plugins en el mismo proceso sin límites de permisos, bloqueos o
    consumo.

  - Intentar resolver scheduling, colaboración remota y multiusuario antes de
    validar sesiones locales.

  - Confundir hooks de plugins con mecanismo de seguridad: la política debe
    imponerse en el host, no ser opcional para el plugin.

  ## 3. Riesgos a largo plazo

  - Congelación del protocolo: si protocol absorbe detalles de cada producto, cada
    cambio romperá plugins.

  - Supply chain de plugins: paquetes maliciosos, dependencias transitivas, robo de
    secretos y ejecución arbitraria.

  - Crecimiento de sesiones: logs, artefactos y contexto pueden convertirse en el
    principal coste de disco y rendimiento.

  - Product packs incompatibles: una funcionalidad de Gold o Music no debe forzar
    dependencias pesadas sobre Code.

  - Aislamiento insuficiente: los plugins de confianza y los de terceros no pueden
    tener el mismo nivel de acceso.

  - Complejidad distribuida anticipada: un control plane remoto solo se justifica
    cuando existan varios clientes, sesiones persistentes o automatizaciones sin
    cliente. El patrón hub–spoke es útil entonces, no antes. Arquitectura hub–spoke
    de Cline (https://docs.cline.bot/sdk/architecture/hub-spoke)

  ## 4. Oportunidades de simplificación

  - Eliminar paquetes iniciales para reasoning, orchestration, model-gateway, tool-
    runtime, context, memory, workspace, storage, scheduler, event-bus,
    observability y ui-kit.

  - Mantener un único contrato de capacidad: modelos, herramientas, almacenamiento,
    recursos, conectores y motores externos son implementaciones de capacidades.

  - Cambiar products/ por product-packs/: manifiestos declarativos, agentes
    habilitados, extensiones permitidas y políticas.

  - Mantener pruebas unitarias junto a cada paquete; reservar tests/ raíz para
    contratos, integración y E2E.

  - Posponer UI compartida hasta que exista una segunda interfaz real que la
    necesite.

  ## 5. Oportunidades de mejora

  - Adoptar tres roles explícitos: cliente, control plane y worker de agentes. Los
    clientes observan y controlan; el control plane coordina; los workers ejecutan.
    VS Code también está separando agentes autónomos en un Agent Host dedicado. VS
    Code Agent Host (https://code.visualstudio.com/docs/agents/concepts/agent-host)

  - Tratar extensiones como módulos con manifiesto versionado, dependencias
    declaradas y carga opcional. IntelliJ demuestra el valor de dependencias
    explícitas y módulos opcionales. IntelliJ Modular Plugins
    (https://plugins.jetbrains.com/docs/intellij/modular-plugins.html)

  - Establecer un único API de control; los workers y clientes no se comunican
    entre sí directamente. Es el patrón que evita acoplamientos laterales en
    Kubernetes. Kubernetes control plane
    (https://kubernetes.io/docs/concepts/architecture/control-plane-node-communication/)

  - Separar el cliente de la ejecución, como Docker separa cliente y daemon.
    Arquitectura Docker (https://docs.docker.com/get-started/docker-overview/)

  - Exigir mantenimiento y compatibilidad de extensiones como responsabilidad
    explícita de sus autores, en vez de añadir extensiones sin dueño. Guía de
    mantenedores Linux
    (https://docs.kernel.org/maintainer/feature-and-driver-maintainers.html)

  ## 7. Justificación técnica

  - Nuevos modelos: se añaden como extensiones que implementan ModelCapability;
    soporte local, nube o híbrido se decide por política y disponibilidad, sin
    cambiar agentes.

  - Nuevos protocolos: se añaden como adaptadores del Capability Protocol. MCP no
    recibe trato especial; es un adaptador más.

  - Nuevas profesiones: añaden product packs y extensiones de dominio, sin
    modificar el control plane.

  - Offline: cliente, control plane, worker, modelos locales y extensiones pueden
    correr en una máquina sin gateway remoto.

  - Solo nube: un adaptador de modelo remoto y un gestor de secretos bastan.
  - Híbrido: la política elige modelo local o nube según permiso, coste,
    conectividad, capacidad y datos sensibles.

  - Escalabilidad futura: el límite cliente/control plane/worker permite pasar de
    proceso local a daemon o servicio remoto sin alterar el protocolo. OpenHands
    también mantiene la UI fuera de la ejecución y del sandbox. OpenHands
    architecture
    (https://github.com/OpenHands/OpenHands/blob/main/docs/architecture.md)

  ## 9. Reglas de dependencia

  protocol                 → no depende de paquetes Piston
  extension-api            → protocol
  client-sdk               → protocol
  control-plane            → protocol
  agent-worker             → protocol + client-sdk
  extension-host           → protocol + extension-api + client-sdk
  apps                     → client-sdk + product-packs
  product-packs            → protocol únicamente
  extensions               → extension-api + protocol

  Reglas adicionales:

  - Ninguna app importa control-plane, agent-worker o extensiones directamente.
  - Ninguna extensión importa otra extensión; declara capacidades requeridas en el
    manifiesto.

  - protocol no importa implementaciones.
  - El control plane no llama código de plugin en proceso propio.
  - Toda acción con archivos, red, procesos o secretos pasa por autorización del
    control plane.

  - Los eventos públicos son versionados, tipados y con dueño; no existe un canal
    libre de eventos.

  - Los unit tests viven junto al módulo; tests/contract protege compatibilidad
    pública.

  ## 10. Criterios de estabilidad

  La arquitectura será estable para iniciar la estructura física cuando se cumpla
  lo siguiente:

  - Cada paquete tiene una responsabilidad de una frase y dependencias permitidas.
  - El Capability Protocol cubre solo capacidades transversales, no semántica de
    productos.

  - Un producto puede añadirse como product pack sin alterar el core.
  - Un modelo local, uno en nube y un conector MCP pueden incorporarse como
    extensiones.

  - Un plugin sin permisos no puede leer secretos, archivos ni ejecutar procesos.
  - Una sesión puede continuar aunque cierre un cliente.
  - El primer flujo local funciona sin servicios remotos: CLI → control plane →
    agent worker → capacidad.

  - Cada decisión de frontera queda registrada en ADR antes de implementar lógica.

  ### ADRs propuestos

  con:

  - ADR-0001: Piston como plataforma compartida y product packs.

  - ADR-0003: Capability Protocol y adaptadores externos.
  - ADR-0004: Extension Host, permisos, activación y compatibilidad.
